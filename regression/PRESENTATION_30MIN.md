## 분 단위 구어체 풀 대본

### [00~04분] 1. 오프닝 — 백엔드 개발자가 본 머신러닝

> 안녕하세요. 저는 Java/Spring 백엔드를 3년 정도 해오다가 이번에 AI 엔지니어 쪽으로 공부 영역을 넓히고 있습니다.  
> 오늘 머신러닝 수학 이론을 강의하려는 게 아닙니다. 저도 처음 공부하면서 **"백엔드 개발자 시선으로 첫 회귀 모델을 만들어 보고, 중간에 밟았던 버그 3개를 어떻게 잡았는지"** 그 과정을 공유하려고 합니다.
>
> 제가 잡은 미션은 단순합니다. 워싱턴 D.C. 공공자전거 2년 치 시간별 데이터(약 17,000건)를 가지고, **"내일 오전 8시에 자전거가 몇 대나 빌려갈지 예측하는 API"**를 만든다고 가정했습니다.
>
> 공부하면서 제일 먼저 머릿속이 정리된 건 이 한 줄이었습니다.  
> 기존 Spring 개발에서는 개발자가 직접 `if (비옴) 대여량 -= 100` 같은 규칙을 코드로 짰습니다. 머신러닝은 반대입니다. **과거 입력(날씨, 시간)이랑 정답(실제 대여량)을 잔뜩 던져주면, 모델이 그 `if-else` 규칙을 알아서 역산해서 만들어 줍니다.**  
> 결국 똑같은 소프트웨어 엔지니어링이었고, 테스트랑 성능 벤치마크 감각이 그대로 통했습니다.

### [04~09분] 2. 데이터 까보기 (Step 1) — `[화면 1 띄우기]`

> 저도 처음엔 바로 모델 코드부터 짜보려고 했는데요. 생각해보니 백엔드 개발할 때도 API 만들기 전에 DB 테이블 스키마랑 `SELECT * LIMIT 10`부터 까보잖아요? 똑같이 데이터부터 열어봤더니 모델 돌리기 전에 벌써 3가지를 건졌습니다.
>
> **첫째, 공식 문서에 버그가 있었습니다.**  
> 데이터 문서에는 `season=1`이 봄이라고 적혀 있었는데, 실제 월을 뽑아보니 12월, 1월, 2월, 3월이고 기온도 제일 낮은 **겨울**이었습니다. 외부 API 명세서만 믿고 개발했다가 운영 장애 나는 거랑 똑같더라고요. 데이터는 무조건 까봐야 합니다.
>
> **둘째, 이 그래프 한 장만 보시면 됩니다.** *(화면 1: 평일 vs 주말 시간대 그래프 가리키기)*  
> 파란 선이 평일, 주황 선이 주말입니다. 평일은 출근 8시랑 퇴근 5~6시에 뾰족하게 쌍봉이 솟고요, 주말은 낮 1시~3시에 완만한 산 하나가 생깁니다. 이 모양을 기억해 두세요. 조금 뒤에 직선 모델이 왜 망하는지 여기서 바로 설명됩니다.
>
> **셋째, 수상한 컬럼 두 개를 찾았습니다.**  
> `casual`(비회원 대여량)이랑 `registered`(회원 대여량)를 더해보니 17,000건 전부 예외 없이 정답(`cnt`)이랑 정확히 똑같았습니다. 그리고 2011년보다 2012년 대여량이 **63% 넘게 성장**해 있었고요.  
> 자, 이 단서들을 들고 본격적으로 모델을 돌려봤습니다.

### [09~20분] 3. 내가 일부러 밟아본 3가지 버그 (Step 2 ~ Step 4)

#### ▶ 기준선 + 버그 1: 점수 100점짜리 가짜 모델 (데이터 누수)
> API 성능 튜닝할 때도 개선 전 p95 응답속도가 있어야 비교가 되잖아요?  
> 그래서 먼저 제일 멍청한 기준선(Baseline)을 잡았습니다. 아무것도 안 배우고 **무조건 과거 평균값으로만 찍기**. 그랬더니 평균적으로 **140대~170대** 정도 틀렸습니다. 평가 지표는 직관적으로 "평균 몇 대 틀렸는지"를 보는 **MAE**를 썼습니다.
>
> 그다음에 일부러 첫 번째 버그를 터뜨려 봤습니다. 아까 본 `casual`이랑 `registered`를 안 지우고 선형회귀에 그대로 넣어봤더니, **오차가 `0.000000대`, 정확도 100%**가 나왔습니다.  
> 모델 내부 가중치를 까보니까 `casual`에 1, `registered`에 1을 곱하고 날씨랑 시간은 전부 `0`으로 무시하고 있었습니다. 그냥 덧셈 계산기가 된 거죠.
>
> 내일 오전 8시를 예측하는 API 요청 JSON에 "내일 비회원 대여량"을 파라미터로 받을 순 없잖아요? 테스트 코드에 정답 객체를 Mock으로 미리 박아두고 단위 테스트 통과했다고 착각한 버그랑 똑같습니다. 이걸 **데이터 누수(Data Leakage)**라고 하더라고요. 두 컬럼을 지웠더니 오차가 104.8대로 현실적인 숫자가 나왔습니다.

#### ▶ 버그 2: 미래를 컨닝하는 랜덤 분할 (`24.9대 → 47.5대`)
> 두 번째 버그가 제일 교묘했습니다. 블로그 예제 그대로 `train_test_split`으로 전체 데이터를 랜덤 8:2로 나누고, `RandomForest` 모델을 돌렸더니 오차가 **24.9대**까지 확 떨어졌습니다.  
> 와, 평균 25대 오차면 바로 배포해도 되겠다 싶었죠.
>
> 근데 테스트 데이터 한 줄을 꺼내서 앞뒤 시간을 조회해 보니 충격이었습니다. **8월 15일 10시랑 12시 데이터는 학습에 들어가 있고, 11시만 시험지에 들어가 있더라고요.** 10시랑 12시 정답을 옆에서 보고 11시를 맞춘 겁니다. 게다가 서비스가 2012년에 63% 성장했는데 2012년 데이터를 다 섞어놨으니 점수가 뻥튀기될 수밖에 없었습니다.
>
> 그래서 **2012년 9월 1일을 기준선**으로 칼같이 잘랐습니다. 과거 20개월로 학습하고 미래 4개월만 맞추게 바꿨더니, 똑같은 모델인데 오차가 **24.9대에서 47.5대로 거의 두 배**가 뛰었습니다. 랜덤 분할 점수만 보고 배포했으면 운영 첫날부터 난리 났겠죠.

#### ▶ 버그 3: 직선 모델의 한계 & 과적합 — `[화면 2 띄우기]`
> 시계열 분할로 제대로 채점한 상태에서 모델 3개를 비교해 봤습니다.
>
> 1. **선형회귀:** 오차가 **136.2대**였습니다. *(화면 2: 평일 3일 그래프 가리키기)* 빨간 점선이 선형회귀입니다. 실제 대여량은 출퇴근 시간에 뾰족하게 솟는데, 선형회귀는 시간 숫자가 커질수록 대여량이 늘어난다고 직선 하나를 긋고 있었습니다. 패턴을 못 담는 **과소적합**입니다.
> 2. **결정트리(DecisionTree):** `if-else` 나무 하나로 바꿨더니 Test 오차가 **59.0대**로 확 줄었습니다. 그런데 학습(Train) 오차를 찍어보니 **0.01대**였습니다. 원리를 배운 게 아니라 기출문제 14,000개를 통째로 외워버린 **과적합**이었습니다.
> 3. **RandomForest:** 나무 100그루에게 각자 공부시키고 평균을 내게 했더니 과적합이 잡히면서 Test 오차가 **47.5대**까지 떨어졌습니다. 파란 선 보시면 출퇴근 쌍봉을 꽤 잘 따라갑니다.

### [20~26분] 4. 에러 분석 & 최종 모델 (`43.62대`) — `[화면 3, 4 띄우기]`

#### ▶ 에러 분석: 블랙프라이데이와 크리스마스 이브 (`화면 3`)
> 여기서 "47.5대 나왔습니다, 끝!" 하고 넘어가기 전에, 백엔드 장애 로그 보듯 **우리 모델이 제일 크게 틀린 날 TOP 5**를 뽑아봤습니다. *(화면 3 가리키기)*
>
> 보니까 `2012년 11월 23일`이랑 `12월 24일`에 무려 **400대씩** 틀렸더라고요. 모델은 490대 탈 거라고 예측했는데 실제론 60~90대밖에 안 탔습니다.  
> 달력을 찾아보고 무릎을 쳤습니다. **11월 23일은 미국 블랙프라이데이(추수감사절 다음 날), 12월 24일은 크리스마스 이브**였습니다.  
> 법정 공휴일이 아니라 DB에 `holiday=0, workingday=1`로 찍혀 있으니, 모델은 평범한 출근일인 줄 알았던 겁니다. 알고리즘이 멍청해서가 아니라 **데이터에 없는 현실 맥락(샌드위치 연휴)** 때문에 틀린 거였습니다.

#### ▶ 피처 엔지니어링 & 최종 벤치마크 (`화면 4`)
> 마지막으로 성능을 더 끌어올려 보려고 세 가지를 실험했습니다. *(화면 4: 벤치마크 표 가리키기)*
>
> 1. **실패한 실험:** "출퇴근 시간 플래그"랑 "시간 주기(sin/cos)" 컬럼을 3개 만들어 붙여봤더니 오차가 `47.5대 → 47.7대`로 오히려 살짝 나빠졌습니다. 트리 모델은 이미 시간과 평일 컬럼으로 잘 쪼개고 있어서 중복 노이즈만 늘어난 거라 과감히 **롤백**했습니다.
> 2. **부스팅 모델 교체:** 나무 100그루가 각자 공부하는 RandomForest 대신, 앞 나무가 틀린 오차를 뒷 나무가 순차적으로 고쳐가는 **`HistGradientBoostingRegressor`**(LightGBM 방식)로 바꾸니 **`45.11대`**로 줄었습니다.
> 3. **운영 DB 과거 이력 피처 추가:** API 서버가 예측하기 직전에 우리 DB에서 **"어제 같은 시간, 1주 전 같은 요일 같은 시간, 2주 전 같은 시간 대여량"** 3개만 조인해서 넣어주는 건 100% 합법이잖아요? 이걸 붙였더니 최종 오차가 **`43.62대`**까지 떨어졌습니다.
>
> 처음 바닥 기준선(`170.51대`)과 비교하면 **오차를 약 74% 줄인 셈**이고, 변수 중요도를 찍어보니 역시 **지난주 같은 시간 대여량**과 **시간대**가 압도적이었습니다.

### [26~30분] 5. Spring 개발자 시선 회고 & 마무리

> 마지막으로 백엔드 개발자 입장에서 이 모델을 실제 서비스에 붙인다면 어떻게 될지 그려봤습니다.  
> 학습 끝난 모델을 `joblib`으로 저장해 보니 파일 크기가 겨우 **약 1MB**밖에 안 됩니다. 이걸 Python FastAPI 추론 서버 메모리에 띄워두고, **Spring Boot 서버가 DB에서 어제·지난주 대여량을 조회해 15개 JSON 피처를 넘기면 10ms 안에 예측값을 받아오는 구조**로 바로 붙일 수 있습니다.
>
> 이번에 머신러닝을 처음 공부하면서 제일 크게 깨달은 건 두 가지입니다.
> 1. **모델 알고리즘 갈아끼우는 것보다, 데이터 누수 막고 검증 기준(시계열 분할) 제대로 세우는 게 훨씬 중요하다.**
> 2. **점수 숫자 하나만 보지 말고, 제일 크게 틀린 로그 5줄을 뜯어보는 습관(에러 분석)**이 백엔드 디버깅이랑 정확히 똑같다.
>
> 다음에는 **분류(Classification)** 주제로 불균형 데이터 함정을 파볼 예정입니다. 질문 있으시면 편하게 물어봐 주세요!

## 예상 질문 Q&A 6선 (실전 방어용)

**Q1. 왜 RMSE 말고 MAE를 메인 지표로 썼나요?**
> "MAE는 '평균적으로 자전거 몇 대 틀렸는지' 바로 와닿아서 기획자나 동료랑 소통하기 좋았습니다. RMSE는 크게 틀린 날(블랙프라이데이 같은 400대 오차)에 제곱 페널티를 세게 주기 때문에, 이상치에 민감하게 관리해야 하는 운영 상황이라면 RMSE도 같이 보는 게 좋습니다."

**Q2. 그럼 블랙프라이데이랑 크리스마스 이브를 피처로 추가해서 다시 학습시키면 더 좋아지지 않나요?**
